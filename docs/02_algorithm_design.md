# fft_conv1d 阶段 2：算法与硬件映射设计

> **历史设计稿。** 本文保留阶段 2 的目标方案和取舍推导，不代表当前 kernel
> 数据流。当前实现状态以 `docs/03_ascendc_v2.md`、Host 与 kernel 源码为准。
>
> 目标平台：Ascend 910B（V220 架构，AI Core = 1 Cube + 1 Vector）
> 对应原型：`python/fft_conv1d_four_step.py`（**已数值验证**，160 个测试通过）
> 上游依据：`算子开发/ops-fft` 的 arch32（910B）实现、本地 CANN API 文档

当前 FFT-GM 与本文目标方案的主要差异：

- 使用 `KERNEL_TYPE_MIX_AIC_1_2` 和 CANN 8.5 默认 KFC 消息驱动；
- 每组只有主 AIV 执行用户数据流，第二个 AIV 注册 Matmul client 后退出；
- 每逻辑核独占 12 个长度 `N` 的 GM 槽，Cube 的 A/B/C 均在 GM；
- 系统 workspace 供 Matmul/KFC 使用，scratch 通过
  `GetUserWorkspace(workspace)` 定位到用户区；
- FFT 按通道 `H` 切核，DIRECT 才按 `B*H` 行切核。

## 1. FFT 分解方案

### 1.1 四步 Cooley–Tukey（N = N1 · N2）

时域下标 `n = n1·N2 + n2`，频域下标 `k = k2·N1 + k1`，`W_M = exp(-2πi/M)`：

```
X[k2·N1+k1] = Σ_{n2} W_{N2}^{n2·k2} · W_N^{n2·k1} · [ Σ_{n1} x_mat[n1][n2] · W_{N1}^{n1·k1} ]
```

| 步骤 | 运算 | 形式 | 单元 |
|---|---|---|---|
| A | `B  = D1 @ x_mat` | `[N1,N1] @ [N1,N2]` | **Cube** |
| B | `B' = B ⊙ T`，`T[k1][n2]=W_N^{k1n2}` | 逐点复乘 | **Vector** |
| C | `C  = B' @ D2` | `[N1,N2] @ [N2,N2]` | **Cube** |

逆变换完全镜像（共轭 + `1/N`）：`E = Y @ conj(D2)` → `E' = E ⊙ conj(T)` → `y_mat = (1/N)·Re{conj(D1) @ E'}`。

### 1.2 三条让这个方案在硬件上成立的性质（均已写成测试）

**性质 1：D1、D2 是对称阵，全程不需要任何转置。**
`D[k][n] = W^{nk} = W^{kn} = D[n][k]`。所以步骤 C 里的 `D2ᵀ` 可以直接写成 `D2`，
逆变换同理。测试 `test_dft_matrix_is_symmetric` 逐位（`atol=0`）验证。

> 实现坑：必须先做**整数**乘再取模生成角度（`-2π·((k·n) mod M)/M`）。
> 若写成 `(-2π·k)·n/M` 这种浮点连乘，因为浮点乘法不满足结合律，
> `(-2π·k)·n ≠ (-2π·n)·k`，DFT 矩阵会出现 ~1e-14 的不对称，性质 1 直接失效。
> 这是本阶段实测踩到并修掉的 bug（原型 `_angle()` 有注释）。取模同时避免了
> `k·n` 高达 `N²` 时三角函数的大幅角规约误差。

**性质 2：频谱停留在置换序 `[k1][k2]`，正逆置换互相抵消，永远不做 digit-reverse。**
`C[k1][k2]` 对应自然序下标 `k = k2·N1 + k1`。因为**频域只做逐点乘**，而逐点乘对
下标置换不变，只要 kernel 频谱用同一套置换存放，就无需还原顺序。
测试 `test_spectrum_is_torch_fft_under_known_permutation` 验证置换关系，
`test_permutation_cancels_end_to_end` 反向验证（故意重排 kernel 频谱必然算错）。
**这省掉了整条链路上所有的重排/转置搬运。**

**性质 3：时域两端都是自然 row-major 布局。**
输入 `x_mat[n1][n2] = x[n1·N2+n2]` 是 `[N1,N2]` 的自然 reshape，输出同理。
所以 GM ↔ 片上的搬运全是**连续大块 DataCopy**，不需要 stride gather。

### 1.3 实输入 / 实输出 + 稀疏跳算

| 优化 | 效果 | 依据 |
|---|---|---|
| 步骤 A 实输入 | 4 次实数 GEMM → **2 次** | `x` 为实数 |
| 步骤 C' 实输出 | 4 次 → **2 次**（只要 `Re{conj(D1)@E'}`） | 输出为实数 |
| 输入零填充跳算 | 步骤 A 收缩维 `N1` → `ceil(L/N2)` | `x_mat` 第 `n1 ≥ ceil(L/N2)` 行全零 |
| kernel 零填充跳算 | 同上，降到 `ceil(K/N2)` | `K ≪ N` 时极显著 |
| 输出裁剪跳算 | 步骤 C' 输出维 `N1` → `ceil(L/N2)` | 只要前 `L` 个时间点 |

合计每行 **12 次实数 GEMM 单位**（2+4+4+2），其中首尾两次还被裁剪削掉一大半。

> **这是 DFT-Matmul 相对蝶形 FFT 的结构性优势**：零填充和输出裁剪在矩阵乘里就是
> "少算几行/几列"，在蝶形 FFT 里完全无法利用（蝶形每一级都会把零扩散到全长）。
> 例如 `L=257, N=512, N2=16`：`R1 = 17` 而 `N1 = 32`，首尾 GEMM 直接省 47%。

### 1.4 (N1, N2) 的选择

代价模型（每行实数 MAC，`R1 ≈ L/N2`）：

```
cost(N2) = 8·N1·N2² + 4·N1·N2·R1 = 8·N·N2 + 4·L·N/N2
d/dN2 = 0  =>  N2* = sqrt(L/2)
```

注意 **最优 N2 明显小于教科书的 sqrt(N)**，因为首尾 GEMM 已被 §1.3 削掉。

三条硬件约束（都写进了 `plan_four_step`，有测试守护）：

1. `N ≥ 256` 时 `N1 ≥ 16` 且 `N2 ≥ 16`（fp32 Cube 分形 16×8，瘦长条 GEMM 浪费分形）。
2. **常量表必须常驻 L1**：`8·(N1² + N2² + N) ≤ 448 KB`。
   这条约束是实测中发现的——`N=8192` 时朴素代价模型选出 `N1=256`，
   而 `D1` 是 `2·256²·4B = 512KB`，正好吃满整个 L1，常量表根本放不下。
   加上约束后选 `N1=128, N2=64`，常量表 224KB，MAC 数**恰好相同**（代价函数在最优点附近很平）。
3. `N` 为 2 的幂，`N ≤ 8192`（仅指本章历史 UB 常驻目标方案）。
   当前设备实现改为 4 的幂：FFT-UB 上限 1024，FFT-GM 仅使用 `N=4096`，
   更大 shape 回退 DIRECT。

实际选择结果：

| L=K | N | N1 | N2 | 常量表 | cube MAC/行 |
|---|---|---|---|---|---|
| 256 | 512 | 32 | 16 | 14 KB | 147,456 |
| 512 | 1024 | 64 | 16 | 42 KB | 393,216 |
| 1024 | 2048 | 128 | 16 | 146 KB | 1,179,648 |
| 2048 | 4096 | 128 | 32 | 168 KB | 3,145,728 |
| 4096 | 8192 | 128 | 64 | 224 KB | 9,437,184 |

### 1.5 方案对比（题目要求的五种路线）

| 方案 | 算力 | 硬件利用 | 结论 |
|---|---|---|---|
| **Vector radix-2/4 蝶形** | 最省，`5N·log2N` flop | Cube 完全闲置；每级都要跨步访存，UB bank 冲突；无法利用零填充/裁剪稀疏性 | ❌ 主路径不用。910B 的 Vector 只有 Cube 算力的几十分之一，省下来的算力换不回吞吐 |
| **Cube 小规模 DFT 矩阵乘（本方案）** | 多 ~10x MAC | Cube 吃满；Vector 只做旋转因子和逐点乘，可与 Cube 重叠；稀疏跳算白送 | ✅ **主路径** |
| **Vector + Cube 混合** | — | 正是本方案：GEMM 在 Cube，旋转/逐点在 Vector，两者流水重叠 | ✅ 已采用 |
| **按 L/K 走不同路径** | — | 小 K 时 direct 更快（见 §10） | ✅ 采用，host tiling 里做分支 |
| **小尺寸 direct，大尺寸 FFT** | — | 同上 | ✅ 采用 |

**为什么不为了用 Cube 而硬上**：本方案的 MAC 数确实是蝶形的约 10 倍
（`N=512`：矩阵乘 ~24.6k 复数 MAC vs 蝶形 ~2.3k）。选它的理由是
Cube 的 fp32 MAC/cycle 比 Vector 高**至少一个数量级**（分形 16×8 vs Vector 256B/cycle），
10 倍算力换 ≥10 倍吞吐仍然划算，而且 Vector 被腾出来做旋转因子从而实现双单元重叠。
这个判断的定量依据见 §10，**其中的 Cube/Vector 算力比 ρ 必须在阶段 5 用实测标定**，
本文所有结论都在 ρ ∈ [8, 32] 区间内给出，不依赖单一取值。

另有一条精度上的旁证：阶段 1 实测中，一次性 O(N²) 大 DFT 矩阵乘的误差约为
分层 FFT 的 2 倍（累加链更长）。四步分解把累加链切成两段，
**既省算力又比单级 DFT 更准**——所以不能为了"一个大 GEMM 更好写"而退回单级。

## 2. 数据布局

### 2.1 GM

| 张量 | 形状 | 布局 |
|---|---|---|
| `input` | `[B, H, L]` | ND 连续，行 `(b,h)` 内 `L` 连续 |
| `kernel` | `[H, K]` | ND 连续 |
| `output` | `[B, H, L]` | 同 input |
| `workspace: 常量表` | `D1[N1,N1]`、`D2[N2,N2]`、`T[N1,N2]` 各复数 | 实虚**分平面**存放（`Xr` 全部在前，`Xi` 全部在后） |
| `workspace: kernel 频谱` | `[H, 2, N1, N2]` | `[k1][k2]` 置换序，实虚分平面 |

**为什么实虚分平面而不是交错**：Vector 的复数乘是 `ar*br - ai*bi` 这种整段对整段的运算，
分平面时两个操作数都是**连续 256B 对齐**的向量，一条 `Mul` 吃满；
交错存放则需要 stride=2 的跨步访问，Vector 效率减半。
（`ops-fft` 的 r2c 用交错，是因为它的输出要直接对外暴露成 `aclfftComplex` 数组；
我们是融合算子，中间频谱不对外，可以自由选更优的布局。）

### 2.2 片上

- **L1（常驻，全部 batch/channel 共享）**：`D1`、`D2`、`T` 的实虚两个平面。
- **UB**：当前 k1 分块的频谱缓冲、kernel 频谱分块、旋转因子分块。
- **L0A/L0B**：GEMM 的分形块，由 Matmul API 或 `LoadData` 管理。
- **L0C**：GEMM 累加器；逆变换末级 GEMM 在此**跨 k1 分块累加**（见 §4）。

## 3. 多核切分

> **当前实现差异：** DIRECT 按 `B*H` 行切；FFT-UB/FFT-GM 按通道 `H`
> 切，每个逻辑核处理该通道的全部 batch，从而在本核复用 kernel 频谱。
> 以下按 `B*H` 的描述是阶段 2 方案，不是当前 kernel。

### 3.1 主策略：按 `R = B·H` 行切分

每个 `(b,h)` 序列的整条 FFT→乘→IFFT 链路完全独立，是天然的并行单位。

```
R = B*H
rows_per_core = ceil(R / GetBlockNum())
本核处理 [blockIdx*rows_per_core, min(R, (blockIdx+1)*rows_per_core))
```

逐条回答题目 §七 的 8 个问题：

1. **每个核负责哪些数据**：一段连续的 `(b,h)` 行。按 `h` 主序编号（`row = h*B + b`），
   使同一核尽量连续处理同一通道的多个 batch —— 这样 kernel 频谱在 UB 里**只算一次、复用多次**。
2. **`B*H` < 核数**：接受部分核空闲。理由：此时总工作量本身就极小
   （`R=1, N=8192` 单核约 9.4M MAC，几微秒），跨核切分要引入的同步开销大于收益。
   备选方案见 §3.2，默认关闭。
3. **单个 FFT 很大**：不靠跨核，而靠**核内 k1 分块 + L0C 累加**（§4.3）解决容量问题。
4. **是否需要跨核同步**：**不需要**。kernel 频谱由每个核为自己用到的通道各算一次
   （冗余度 ≤ `(H+P)/(B·H)`，`P` 为核数），换掉一次 `SyncAll` 全局栅栏。
   若实测显示冗余占比过高（`B` 很小而 `H` 很大时），再切换到
   "prologue 分核算 kernel 频谱 → `SyncAll` → 主循环"的版本，`SyncAll` 已确认可用。
5. **避免多核写同一输出**：行切分下每行输出只由一个核写，**完全不需要原子加**
   （符合题目"优先避免原子加"的要求）。
6. **减少 GM↔UB 搬运（历史目标）**：中间频谱全程不落 GM（§9）；常量表常驻 L1；
   kernel 频谱按通道在 UB 内复用。当前 FFT-GM 会把中间结果落入每核独占的 GM 槽。
7. **连续访存与对齐**：性质 3 保证时域两端都是自然 row-major，
   每行 `L` 个 fp32 连续搬运。行首地址 `(b·H+h)·L·4` 字节，
   `L` 不是 8 的倍数时行首不满足 32B 对齐 → 用 `DataCopyPad` 处理（见第 8 点）。
8. **尾块**：两处。
   (a) 行数尾块：`R % P != 0`，用上界裁剪，最后一个核少处理几行；
   (b) 长度尾块：`L % N2 != 0` 时 `x_mat` 最后一个有效行只有部分有效数据，
   用 `DataCopyPad` 搬入并由 `SetPadValue(0)` 补零，
   补的零天然就是 FFT 需要的零填充，**不需要额外清零**。

### 3.2 备选：`R` 很小时按 k1 分块跨核（默认关闭）

步骤 A/B/C、逐点乘、逆步骤 A'/B' **全部按 k1 行独立**，可以自由跨核切。
唯一的障碍是逆变换末级 `y_mat = Σ_{k1} conj(D1)[n1][k1]·E'[k1][n2]` **在 k1 上求和**，
跨核切分就需要归约。两个选项：

- 各核把部分和写 workspace，再 `SyncAll` + 一个核做归约 —— 无原子加，但多一次 GM 往返；
- 用 atomic add 直接累加到输出 —— 与题目要求冲突，不采用。

结论：默认不开；仅当实测显示 `R < P` 且 `N ≥ 4096` 的场景确实重要时，
再启用第一种（阶段 5 评估）。

## 4. UB / L1 / L0 数据流与 Tile

### 4.1 一行的完整流水

```
GM ──DataCopyPad──> UB: x_pad[N]         (补零由 SetPadValue 完成)
                      │
      [Cube] 步骤A: D1(L1) @ x_mat(UB,VECOUT) ──> L0C ──Fixpipe──> UB: Br,Bi
                      │
      [Vector] 步骤B: (Br,Bi) ⊙ T(UB)  4次Mul+2次Add，原地
                      │
      [Cube] 步骤C: B'(UB) @ D2(L1) ──> L0C ──> UB: Cr,Ci
                      │
      [Vector] 逐点乘: (Cr,Ci) ⊙ (Kr,Ki)(UB)
                      │
      [Cube] 逆A': Y(UB) @ conj(D2)(L1) ──> L0C ──> UB: Er,Ei
                      │
      [Vector] 逆B': (Er,Ei) ⊙ conj(T)
                      │
      [Cube] 逆C': conj(D1)(L1) @ E'(UB) ──> L0C ──Fixpipe──> GM: output[0:L]
```

关键点：Matmul 高阶 API 允许 A 矩阵位于 `TPosition::VECOUT`（已核对文档），
所以 **Vector 算完的中间结果直接作为下一个 GEMM 的输入，不经过 GM**。
整条链路 GM 只被碰两次：读 input、写 output。

### 4.2 行间流水与 double buffer

Cube 和 Vector 是两个独立单元。把行分成 tile，让第 `i` 行的 Vector 阶段
与第 `i+1` 行的 Cube 阶段重叠：UB 上开两套频谱缓冲做 ping-pong。
`Matmul` 高阶 API 自身会在 L1/L0 上做 ping-pong；行级 double buffer 由 `TQue` 的深度 2 提供。

### 4.3 k1 分块 + L0C 累加（大 N 的容量方案）

步骤 A 输出的 `k1` 行、旋转因子、步骤 C、逐点乘、逆 A'/B' **全部按 k1 行独立**；
只有逆 C' 在 k1 上求和。于是可以按 `KB1` 大小的 k1 块流式处理：

```
for kb in range(0, N1, KB1):
    ... 对这块 k1 做 A→B→C→乘→A'→B' ...
    逆C' 的 GEMM 以 initC=(kb==0) 累加进同一块 L0C
最后一次性 Fixpipe 到 GM
```

L0C 累加是 `Mmad`/`Matmul` 原生支持的（`initC=false`），**没有额外代价**。
这样 **UB 占用与 N1 无关**，只与 `KB1·N2` 有关，是支持大 N 的关键。

### 4.4 Tile 大小与容量核算（fp32）

以 `L=K=1024 → N=2048, N1=128, N2=16` 为例：

| 缓冲 | 大小 | 位置 |
|---|---|---|
| `D1` 实虚 | `2·128²·4 = 128 KB` | L1（常驻） |
| `D2` 实虚 | `2·16²·4 = 2 KB` | L1（常驻） |
| `T` 实虚 | `2·2048·4 = 16 KB` | L1→UB 分块 |
| 频谱缓冲 ×2（ping-pong） | `2·2·2048·4 = 32 KB` | UB |
| kernel 频谱 | `2·2048·4 = 16 KB` | UB |
| 输入行 | `2048·4 = 8 KB` | UB |

UB 合计约 72 KB / 192 KB，可以再开 2 行的 double buffer（约 144 KB）。

L0C 校验：逆 C' 的输出块 `[R1_out, N2] = [64, 16]` 每分量 1024 float = 4 KB，
远小于 128 KB。L0A/L0B：步骤 A 的 `[N1, R1] = [128, 64]` = 32 KB ≤ 64 KB ✔。

**`MAX_N_FFT = 8192` 的由来**：不做 k1 分块时，`N=8192` 下
旋转因子 64 KB + kernel 频谱 64 KB 就占掉 128 KB，只剩 64 KB 放数据，
连一套 ping-pong 都开不起。开启 §4.3 的 k1 分块后这个上限可以放宽。

> ⚠️ **本节的 8192 只适用于本章历史的"中间结果常驻 UB"目标方案。**
> 当前实现取 4 的幂：FFT-UB 支持 `N<=1024`；FFT-GM 当前仅支持 `N=4096`，
> 并使用每逻辑核 12 个长度 `N` 的用户 GM 槽。`N>4096` 自动回退 DIRECT。
> 4096 是 FFT 路径上限，不是算子 shape 硬上限。

### 4.5 一个必须诚实说明的隐患

步骤 C 与逆 A' 的 GEMM 形状是 `[R·N1, N2] @ [N2, N2]`，**收缩维只有 `N2`（16~64）**。
这是"瘦 K"GEMM，算术强度低（每个输出元素只有 `N2` 次 MAC），
Cube 很可能达不到峰值，瓶颈会落在 L1→L0 的载入带宽上。
纯 MAC 最优的 `N2` 因此**偏小**；真实最优 `N2` 应该比 §1.4 的解析解更大。
`plan_four_step` 已把下限做成可调参数，**具体取值必须在阶段 5 用实测标定，不在此拍板**。
多行批处理可以缓解：步骤 A 可以把多行拼成 `[N1, R1] @ [R1, R·N2]` 一次算，
步骤 C 拼成 `[R·N1, N2] @ [N2, N2]`，把 M 维做大。

## 5. 旋转因子的生成与存储

- **生成**：`W = exp(-2πi·((k·n) mod M)/M)`，**先整数乘再取模，用 fp64 算三角函数，最后转 fp32**。
  两条理由见 §1.2 的实现坑（对称性 + 大幅角规约）。
- **在哪生成**：`D1`、`D2`、`T` 只依赖 `N1/N2/N`，与输入数据无关。
  但自定义算子的 host tiling 阶段不能直接往 GM 写大块数据，因此方案是
  **device 侧 prologue 生成**：由 `blockIdx == 0` 之外的各核分工用 `Sin`/`Cos` 向量指令
  生成自己那部分并写 workspace。若实测生成开销可忽略（表很小，且每次调用都要重算），
  再考虑把表提升为算子的常量输入以彻底消除重复生成 —— 阶段 5 决定。
- **存储**：实虚分平面（§2.1），L1 常驻，全核共享。
- **容量**：见 §1.4 表，最大 224 KB。

## 6. RFFT / IRFFT 流程与共轭对称

### 6.1 首版本：不利用 Hermitian 对称

在置换序 `[k1][k2]` 下，`X[N-k] = conj(X[k])` 映射成
`(k1,k2) → (N1-k1, N2-k2-1)`（行翻转 + 列翻转带偏移），
半谱对应的是一个**不规则的三角形区域**，无法切成规整的 Cube tile。
强行利用会把规整 GEMM 打碎，得不偿失。

首版本因此计算全部 `N` 个频点。注意这**不等于浪费一倍**：
§1.3 的实输入/实输出特化已经把首尾两次 GEMM 从 4 次降到 2 次，
把实数性的收益拿到了大头。

### 6.2 阶段 5 的做法：batch 配对打包（已在原型中验证）

把**同一通道的两个 batch** 打包成一路复序列 `z = x_{b1} + i·x_{b2}`：

```
Z[k] = X1[k] + i·X2[k]                        (DFT 线性)
Z[k]·K̂_h[k] = X1[k]K̂[k] + i·X2[k]K̂[k] = Y1[k] + i·Y2[k]
IDFT 后：Re = y1, Im = y2
```

**因为配对的两行共享同一个 kernel `K̂_h`，经典的 Hermitian 拆分/合并被完全省掉**，
也就不需要 `conj(Z[N-k])` 这种反序访问（Vector 上要靠 `Gather` + 索引表，代价很高）。

代价对比（每 2 行）：不打包 `2×(2+4+4+2)=24` 个 GEMM 单位，打包后 `4+4+4+4=16`，**1.5x**。
`B` 为奇数时最后一行退回实输入路径。
`fft_conv1d_four_step_packed` 已实现并通过测试（含 `B=5` 奇数、`B=1` 退化）。

### 6.3 DC / Nyquist / 归一化

- 本方案走**全谱复数**路径，DC 与 Nyquist 不需要特殊分支（它们只是 `k1=k2=0` 和某个固定格点，
  虚部自然为 0）。这比半谱 RFFT 少一类边界代码。
- 归一化 `1/N` 只出现一次，放在逆变换末尾。也可折叠进 `conj(D1)` 表里省一遍 Vector `Muls`；
  但 fp16/bf16 下预缩放会压缩动态范围，低精度版本再定。

### 6.4 复数乘法：3 次实乘 vs 4 次实乘

**结论：Vector 上用 4-mul，Cube 上用 3-mul。** 两个单元的瓶颈不同：

| 位置 | 选择 | 理由 |
|---|---|---|
| Vector 逐点乘（旋转因子、频域乘） | **4-mul** | Vector 的瓶颈是 UB 带宽和指令数，不是乘法器。3-mul 要多 3 次加减和 2 个临时 buffer，UB 压力更大；且 `t3-t1-t2` 有抵消误差，fp16/bf16 下风险明显 |
| Cube 复数 GEMM（步骤 C、逆 A'） | **3-mul（Karatsuba）** | 这里矩阵乘本身就是全局瓶颈，4 次 GEMM → 3 次是**实打实省 25% Cube 时间**，额外的矩阵加法在 Vector 上顺带做掉 |

首版本先用 4-mul 保证正确性，Cube 侧的 3-mul 放在阶段 5（原型里 `complex_mul` 已同时实现两种并有一致性测试）。

## 7. 复杂度分析

每行（一个 `(b,h)`）的实数 MAC 数：

```
cube_mac = 8·N1·N2²  +  2·N1·N2·R1_in  +  2·R1_out·N1·N2
         ≈ 8·N·N2 + 4·L·N1
vector_flop ≈ 18·N       (正逆旋转因子各 6N + 频域逐点乘 6N)
```

| B,H,L,K | N | N1 | N2 | cube MAC | vector FLOP | 与直接卷积误差 |
|---|---|---|---|---|---|---|
| 1,1,16,3 | 32 | 32 | 1 | 2,624 | 768 | 1.19e-07 |
| 2,3,31,7 | 64 | 8 | 8 | 37,248 | 8,064 | 9.54e-07 |
| 4,8,64,1 | 64 | 8 | 8 | 214,016 | 39,936 | 9.54e-07 |
| 1,5,100,32 | 256 | 16 | 16 | 286,720 | 30,720 | 1.91e-06 |
| 2,16,257,17 | 512 | 32 | 16 | 3,768,320 | 344,064 | 2.86e-06 |
| 2,4,1024,128 | 2048 | 128 | 16 | 6,946,816 | 344,064 | 1.14e-05 |

误差与阶段 1 的 `torch.fft` 路径同量级（相对误差 ~1e-7），说明分解没有引入额外精度损失。

## 8. GM 搬运量分析

**融合算子的最小搬运量**（中间频谱全程不落 GM）：

```
GM_bytes = 4·(2·B·H·L + H·K) + 常量表与 kernel 频谱的一次性往返
```

与"调用三个独立算子（rfft → mul → irfft）"对比，后者每行要额外往返
2 个复数频谱 ≈ `8N` 个 float：

| 场景 | 融合（本方案） | 非融合三算子 | 倍数 |
|---|---|---|---|
| `L=1024, N=2048` 每行 | 8 KB | 8 KB + 64 KB | **9x** |

算术强度（`L=K=1024`）：`1,179,648 MAC ÷ 8192 B ≈ 144 MAC/byte`，
**深度计算受限**，GM 带宽不会成为瓶颈 —— 这也说明把三步融合进一个自定义算子是正确的工程选择。

## 9. Direct Conv 与 FFT Conv 的分界点

### 9.1 为什么 depthwise direct conv 只能走 Vector

`y[b,h,t] = Σ_j x[b,h,t-j]·k[h,j]`，每个通道只有一个 filter。
im2col 后是 `[L, K] @ [K, 1]` 的**矩阵-向量**乘（`N=1`），Cube 分形 16×16 完全用不上。
按 batch 拼也只是把 M 做大，`N` 恒为 1。
所以 direct 路径的合理实现是 Vector：`for j in range(K): y[j:] += x[:L-j]·k[j]`，
`L·K` 次 MAC，全部走 Vector 的 FMA。

### 9.2 分界点

令 `ρ = Cube 的 fp32 MAC/cycle ÷ Vector 的 fp32 MAC/cycle`（910B 上约 8~32，**待阶段 5 实测标定**）。
FFT 路径的等效 Vector 周期数 `= cube_mac/ρ + vector_flop`，direct 为 `L·K`。

**K\*（FFT 开始占优的最小 K）：**

| L | ρ=8 | ρ=16 | ρ=32 |
|---|---|---|---|
| 64 | 65 | 65 | 58 |
| 128 | 108 | 78 | 63 |
| 256 | 117 | 82 | 65 |
| 512 | 133 | 90 | 69 |
| 1024 | 166 | 106 | 77 |
| 2048 | 212 | 130 | 89 |
| 4096 | 277 | 162 | 105 |
| 8192 | 372 | 210 | 129 |

**长卷积场景 `K = L`（Hyena / S4 / FlashFFTConv 的典型区间）的加速比（ρ=16）：**

| L=K | direct MAC | FFT 等效 | 加速比 |
|---|---|---|---|
| 256 | 65,536 | 21,504 | 3.0x |
| 512 | 262,144 | 49,152 | 5.3x |
| 1024 | 1,048,576 | 122,880 | **8.5x** |
| 2048 | 4,194,304 | 294,912 | **14.2x** |
| 4096 | 16,777,216 | 786,432 | **21.3x** |
| 8192 | 67,108,864 | 1,966,080 | **34.1x** |

### 9.3 结论与分派策略

- **`K < 64` 一律走 direct**：在任何 ρ 下 FFT 都不占优。题目给的 5 个测试 shape
  （`K = 1,3,7,17,32`）**全部落在 direct 区间**——这一点必须说清楚，
  它们是正确性用例，不是性能用例。
- **`K ≳ 128` 且 `L ≥ 256` 走 FFT**，收益随 `K/L` 增大迅速放大。
- **中间地带（64 ≤ K < 128）**用 tiling 里的查表分派，阈值在阶段 5 用实测曲线定，
  上表作为初值。
- 分派在 **host tiling 阶段**完成（写进 TilingData 的 `algo` 字段），kernel 侧按分支走，
  避免 device 上的动态判断。
